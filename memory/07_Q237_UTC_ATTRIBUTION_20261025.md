## Факты (01_STATE)

Дефект Issue #237: на UTC-rollover базой нового дня становился **последний наблюдённый** streak, а не
streak, живший в момент полуночи. `23:59:59.200Z -> 00:00:00.300Z` давал новому дню целую секунду
(`dayMetrics.q_nodmg = 1`), хотя внутри нового дня было живо всего 0.300 s streak. Старый baseline был
`59 s` вместо физических `59.8 s`.

Починка (только quest core, без bump версии сейва): в записи появился `lastTickAtMs` — wall clock
последнего принятого streak-sample; `QuestEngine.streakAtDayStart()` делит интервал наблюдения по
полуночи текущего дня (`credited = min(advance, currentAt - dayStart)`), и базой нового дня становится
streak, живший в полночь. Новый и восстановленный забег сбрасывают якорь.
`src/platform/GameHostLifecycle.ts` и `src/game/collection/ClientCollection.ts` не тронуты; наград, Daily,
экономики, платежей, деплоя и production нет.

Новые гейты: `npm run test:quest-utc-attribution` (независимая календарная эталонная модель) и
`npm run test:quest-utc-attribution-mutations` (13/13 killed, 3 эквивалентных, 1 control unchanged,
Asia/Tokyo). Оба подключены к существующим CI-шагам через `package.json` (`test:quest-core` и
`test:quest-core-mutations`), потому что приложение не может записать `.github/workflows/**`.
Существующий quest core gate сохранён на **86/86 killed + 1 control unchanged**. F-5 terminal force
(`59 -> 60`) не сломан. Полный отчёт: `docs/qa/QUEST_Q237_UTC_ATTRIBUTION_20261025.md`.

## Решения (02_DECISIONS)

1. Wall clock решает, какой UTC день; streak остаётся измеренным в run clock. Wall clock только
   находит полночь внутри интервала наблюдения и никогда не подменяет игровую длительность.
2. База нового дня — streak, живший **в полночь**. Зачисляемая часть интервала:
   `min(advance, время нового дня внутри интервала)`: streak никогда не растёт быстрее wall clock и не
   может быть зачислен в день, в котором он не набежал.
3. Продюсер **не** менялся. Wall clock сэмпла — это момент, когда движок его получил, и ротация дня
   идёт по тому же часу в тот же момент; смешивать время наблюдения одного сэмпла со временем доставки
   другого значило бы записать сэмпл в день, из которого движок уже ушёл.
4. Поддержка скачков системных часов не выдумывалась: часы назад не откатывают день (как и раньше), часы
   вперёд не поддерживаются, пауза через полночь локализуется только как «новый день». Все допущения
   перечислены в QA-отчёте.
5. `q_time` сохраняет прежнюю форму rollover: #237 определяет дефект на streak, а время выживания —
   это run-scoped пик, чья база берётся из счётчика забега на rollover, и существующий контракт это
   фиксирует. Записано как связанное, неизменённое ограничение — не молча.
6. Версия сейва остаётся **4**: новое поле опционально и санитизируется при чтении, запись версии 1–3
   читается обычным путём, и её первый сэмпл не делится.
