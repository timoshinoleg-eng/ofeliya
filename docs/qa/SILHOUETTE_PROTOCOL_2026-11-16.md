# Протокол «5 секунд на силуэт» — читаемость игрока в плотном поле

**Статус:** принят как QA-инструмент (I-07, research brief 2026-11-16).
**Дата базовой линии:** 2026-11-16, main @ 2bd6320.
**Код:** `scripts/silhouette-probe.cjs` (browser-проба), `scripts/lib/silhouette-metrics.cjs` (метрики),
`tests/silhouette-metrics.mjs` (контрактный тест математики), CI-шаг «Silhouette readability probe».

## Зачем

Читаемость игрока при 150–200 врагах до этого не измерялась ничем, кроме формы элит.
Этот протокол — воспроизводимая половина проверки; вторая половина — человеческая (ниже).

## Сценарий автоматической пробы

1. 390×740, оба рендерера (`?renderer=webgl` / `?renderer=canvas`), dev-сервер проекта.
2. GameScene стартует; проба на сессию глушит: спавн волн (`wave.update`), автоогонь
   (`tryFire`), начисление XP (`addXp`) — иначе убийства открывают мутационную
   модалку поверх кадра (поймано отладкой: снапшот снимал модалку, а не бой).
3. Свои 200 врагов спавнятся через публичный `GameScene.spawnEnemy` по
   детерминированному layout (mulberry32, сид 20261116): 125 swarm (8 элит),
   45 runner, 30 brute (2 элиты); 65 % кольцом 170–330 px, 35 % в четырёх
   фиксированных плотных карманах. Открывающие волны директора очищаются —
   поле только наше.
4. Камера принудительно ставится на игрока (follow-lerp 0.14 иначе даёт
   разбегание ±30 px между прогонами), 300 мс посадки, затем `scene.pause('Game')`
   через SceneManager (ScenePlugin.pause() без ключа — молчаливый no-op, поймано
   отладкой: `isPaused` оставался false, поле жило и дрейфовало).
5. Кадр читается через `renderer.snapshot` (WebGL отдаёт HTMLImageElement,
   Canvas — canvas; нормализуется в 2D-контекст). Метрики считаются в Node
   одной линейкой (`scripts/lib/silhouette-metrics.cjs`) — в страницу не инжектится.
6. Повторяемость: два полных прогона (перезагрузка страницы) на рендерер,
   расхождение по ключевым метрикам < 10 %.

## Метрики (автоматический прокси)

Спрайт аватара мал (~50 px), «рваный» и полупрозрачный: наивный медианный
центр даёт разбег >80 % между прогонами (поза дыхательной анимации), а p90
всей внутренней коробки — это фон, т.к. аватар занимает её меньшинство.
Поэтому аватар характеризуется своими **самыми яркими** пикселями:

| Метрика | Определение |
|---|---|
| `signalLum` | p99 яркости во внутренней коробке 44×44 (хайлайт аватара; враги держат дистанцию ≥100 px и p99 не могут перехватить) |
| `contrastMean` | WCAG-контраст `signalLum` к средней яркости кольца 40–70 px (за пределами свечения и silhouetteClearing) |
| `contrastP90` | то же к p90 кольца (яркий сосед не должен «утопить» аватар локально) |
| `playerArea` | площадь пикселей цвета хайлайт-кластера (медиана топ-5 % по яркости) в коробке 160×160 |
| `uniqueness` | `playerArea / max(площади конкурирующих оттенков)` — danger red, cyan, orange, purple, rna/state green, gold (белые оттенки исключены: иначе метрически совпадают с самим аватаром) |

Тёмный аватар честно даст контраст ≈1.0 — «яркого сигнала нет» это результат,
а не артефакт сэмплинга.

## Базовая линия (2026-11-16, 390×740, 200 врагов)

| Рендерер | contrastMean | contrastP90 | uniqueness | playerArea | maxCompetitor |
|---|---|---|---|---|---|
| webgl | 10.08 / 10.14 | 9.19 / 9.26 | 1.08 / 1.07 | 119 / 118 | 110 |
| canvas | 10.34 / 10.92 | 8.85 / 9.55 | 1.07 / 1.08 | 122 / 123 | 114 |

Повторяемость: расхождение прогонов < 6 % по всем ключевым метрикам (норма < 10 %).

**Гейты пробы:** contrastMean ≥ 7.0, contrastP90 ≥ 6.0, uniqueness ≥ 1.0
(залочено ~30 % запаса по контрасту; uniqueness держит дизайн-пол 1.0 намеренно).

## Выводы базовой линии

1. **Яркостной сигнал силён:** контраст хайлайта к локальному фону ≈10:1 на
   обоих рендерерах — silhouetteClearing + glow делают работу (A1/A2 подтверждено
   числом, а не глазами).
2. **Цветовая уникальность — на грани:** uniqueness ≈1.08, площадь хайлайта
   ~120 px против ~110 px у сильнейшего конкурента в той же окрестности.
   Это количественное подтверждение гипотезы I-10 (развести игрока и
   подборы/угрозы по яркости/цвету на 8–12 %) — запаса почти нет.
3. Деградацию читаемости на DPR≠1 этот протокол не покрывает (пиксель-в-пиксель
   читает backing store 1:1); HiDPI — отдельный трек (P-11/PR #282).

## Человеческая половина (критерий и выборка)

Автоматика — прокси. Продуктовый критерий остаётся за наблюдателем:

- **Выборка:** N = 5 наблюдателей, не знакомых с текущей работой над силуэтом.
- **Протокол:** тот же замороженный кадр (или живой 5-секундный фрагмент того
  же поля) показывается 5 с; вопрос: «укажи, где игрок». Порядок полей —
  случайный, между показами — пауза с нейтральным кадром.
- **Критерий принятия:** ≥ 4/5 наблюдателей локализуют игрока верно за ≤5 с
  на каждом из двух рендереров. Провал ≥2 наблюдателей на одном рендерере =
  баг читаемости, несмотря на зелёные гейты пробы.
- Материал для показа: артефакт пробы может сохранять кадр (`--save-frame`),
  либо использоваться живой прогон через `?renderer=`.

## Как запускать

```bash
npm run dev -- --host 127.0.0.1 &          # или любой сервер на 5173
node scripts/silhouette-probe.cjs           # OFELIYA_BASE_URL / SILHOUETTE_ARTIFACT — опционально
npm run test:silhouette-metrics             # математика метрик без браузера
```

Артефакт: `artifacts/silhouette-baseline.json` (в .gitignore, как и
mobile-acceptance.json — замер, не код).

## Ограничения

- Замороженное поле, не живой бой: метрика про «силуэт в плотности», не про
  motion-читаемость (живую динамику покрывает человеческая половина).
- Один viewport (390×740) — выбор брифа; 320×568 можно добавить параметром
  позже, гейты пересчитать той же пробой.
- QA-инструмент: глушение wave/tryFire/addXp — только внутри прогона пробы,
  прод-гейтов не касается.
