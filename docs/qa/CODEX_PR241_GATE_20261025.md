## Verdict on the original candidate: BLOCK on the specified adapter-transfer contract

### P2: returning to the previously announced Telegram SDK loses Game lifecycle

Evidence: the original cross-flow passes after Telegram → MAX → Browser → Telegram, but ends
with `activatedHandlers: 1`. That is only TelegramPlatform's swipe-lock listener; the Game
lifecycle was already lost. The finish assertion compared the count against the already broken
pre-finish state and passed without removing any Game handler.

RED: add assertions for `deactivated === 1` and closing confirmation on return, without changing
product code. `test:muse-convergence-crossflow` fails with
`returning to Telegram must restore the Game host lifecycle`, actual `0`, expected `1`.
An independent real-game probe also observes `closing: false` after return.

Root cause: `GameHostLifecycle.bind` destroys its controller on MAX ready, but only listens for
bridge-ready events. ViewportManager detects adapter return on resize. The loader announces each
SDK object only once, so returning to the same Telegram object does not trigger another ready.

Minimal fix: subscribe/unsubscribe `bind` to resize as well. Existing identity checks keep the
binding idempotent. No new timer, polling, dependency or ownership mechanism is added.

GREEN: the strengthened cross-flow restores one Game deactivation handler and closing confirmation
on first return and on all three switching rounds, exercises actual pause/resume after return,
then verifies finish removes exactly one activation handler (2 → 1) and all Game deactivation
handlers (1 → 0). No assertion or timeout was relaxed.

Scope of severity: P2 against the adapter-transfer acceptance contract explicitly requested for
this gate and exercised by the candidate's advertised cross-flow. This is inherited from #240,
not introduced by the synchronous-pause change. The host globals are synthetic in desktop tests;
an actual Telegram/MAX client deleting and restoring those globals was NOT observed. This is
not evidence of an ordinary native Telegram background/foreground failure. A separate static
reviewer agreed with the defect/fix but would classify it P3 absent the explicit transfer contract.

## Independent answers about MiniMax's product changes

1. **The deferred-pause defect is real.** A separate harness uses real installed Phaser 3.90
   SceneManager/ScenePlugin/Systems, controlled scenes and the unchanged product lifecycle.
   On #240: same-turn deactivate/activate leaves RUNNING immediately, then PAUSED after the next
   actual `poststep`. On #241: deactivation is immediately PAUSED, activation immediately RUNNING,
   and it remains RUNNING after the next step. No mock implements the scene queue.
   Additionally, the original #241 cross-flow script was loaded verbatim from Git and run
   against the untouched #240 Vite tree: it fails the exact same-turn ownerless-pause assertion,
   with `before.active=true`, then `paused=true`, `modalOpen=false`, `canResumeFromHost=true`.
   The same original script passed against #241 before the follow-up patch.
2. **The chosen API is public, but deliberately bypasses the queue.** Installed Phaser is exactly
   3.90.0. ScenePlugin lines 539/564 call `queueOp`; SceneManager lines 1032/1058 call Systems
   directly. Manager pause/resume do not mutate the scenes array. Phaser's class-level comment
   discourages direct manager use in general because of queue ordering; this is an audited narrow
   exception, not permission to convert unrelated scene operations. No new reachable ownership or
   shutdown/restart regression was found. Official source:
   [ScenePlugin](https://github.com/phaserjs/phaser/blob/v3.90.0/src/scene/ScenePlugin.js),
   [SceneManager](https://github.com/phaserjs/phaser/blob/v3.90.0/src/scene/SceneManager.js).
3. **The cap is bounded-window idempotency.** Independent tests confirm both parse and observe
   retain the newest 1024 valid distinct IDs. #240 retains 1025 in the paired control. Parsing a
   2000-ID legacy record retains `parse-976` through `parse-1999`; malformed input, future schema
   read-only behavior, and throwing quota storage were checked independently.
4. **An evicted ID is counted again.** Observing `old` with 250 kills/13 elites, then 1024 other
   IDs, then `old` again changes runs 1025 → 1026, kills 250 → 500 and elites 13 → 26, unlocking
   `killer_500`, `stars_500` and `skin.gilded-prime`. #240 suppresses that replay. Unlock IDs already
   present are not awarded twice, but a cumulative threshold can be crossed early.
   These local unlocks persist and there is no revoke UI: cosmetic-only does not make that replay
   semantically harmless. There is no money,
   authoritative score, wallet, permanent power or server state changes. `GameScene.finish` is
   synchronous, guards `runResult`, clears the checkpoint, and is the only product caller;
   fresh runs get fresh identities. No ordinary single-page path delivers a 1024-runs-old finish.
   A very old concurrent tab/checkpoint replay lies outside that horizon and the existing
   single-tab model. **P3 contract limitation**, not proof of unconditional lifetime idempotency;
   no cap rewrite is included in this patch.

  terminal times; this proves downstream producer/terminal integration, not natural progression.

  taps also retry. Loops are finite, but the nested waits do not implement one global small
  timeout. They can hide transient interaction failures and do not prove first-tap reliability.
  The skins pager loop has no explicit iteration bound. Workflow timeout is unchanged at 25 min.

  `net::ERR_FAILED` or the 503 phrase, including page errors. It should match the intercepted API
  request/status, and page errors should normally remain unfiltered. In the independently passed
  original run there were zero page errors and the distinct console error was exactly the
  intentionally fulfilled `/api/**` HTTP 503. No observed unexpected error is being dismissed.
- CPU throttle only changes scheduling; it does not change assertions/timeouts or product code.
- **P3:** direct `SceneManager.remove('Game')` emits DESTROY without SHUTDOWN. A controlled real
  Phaser test retains one lifecycle listener after direct removal; callbacks do not throw against
  an absent Game key. Normal Game restart/Menu/finish call cleanup, which was exercised. No
  shipped active-Game removal/replacement path was found; do not claim generic DESTROY cleanup.
  This patch does not broaden into that separate lifecycle design change.
- No new production test seam was added. Existing `__game` probes are DEV or explicit visual QA
